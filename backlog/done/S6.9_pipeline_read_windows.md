# S6.9 — Pipeline read windows: stats cap + audit window

**Epic:** Sprint 6 / self-host E2E — hardening follow-up (from S6.6a review)
**Estimated effort:** ~1.5 h

## Goal

Remove two silent truncations in `services/pipeline.py` flagged by the S6.6a
review gate: `pipeline_stats` derives counts over a 1000-row window, and
`get_match_detail` scans only the user's last 200 audit rows. Past those
limits the dashboard silently undercounts / loses old events.

## Spec

- `pipeline_stats`: SQL `COUNT` aggregation (per-stage counts in the database,
  both dialects) instead of Python-counting a capped window; keep the pure
  `derive_stage` mapping as the single source of stage vocabulary (a SQL
  CASE expression must mirror it — add a parity test that both agree on a
  seeded matrix).
- `get_match_detail`: fetch audit rows filtered by finding/application in SQL
  (e.g. `detail LIKE` is dialect-fragile — prefer a per-row Python filter over
  a *finding-scoped* pre-filter, or store a `finding_id` column on audit_log
  via migration if the LIKE approach is rejected) — decide on the card at
  implementation; the outcome must be: no event for the finding is lost
  regardless of how many unrelated audit rows exist.
- Tests: seed > window sizes and prove counts/events stay correct.

## Improvements noted

- **Decision (card left it open):** LIKE pre-filter route chosen over an
  `audit_log.finding_id` migration. The LIKE is a superset pre-filter keyed on
  the exact `"key": value` shape `json.dumps` writes; the exact per-row Python
  filter is unchanged, so no event is ever lost and no migration/call-site
  churn was needed. Documented in `pipeline.py`.
- `pipeline_stats` now aggregates per-stage counts in SQL
  (`_STAGE_COUNTS_SQL`); the pure `derive_stage` remains the stage vocabulary
  source of truth, with a 320-combo seeded-matrix parity test (5 finding
  statuses × 8 app states × 8 outcomes, incl. `""` and unknown outcomes)
  pinning the SQL CASE to it on both dialects.
- `_iso_ms_z` formats the week boundary in the exact shape SQLite's strftime
  defaults write (fixed-width ms + `Z`), so lexicographic text comparison IS
  chronological on SQLite; PG coerces the same string to TIMESTAMP (probed
  empirically via psycopg before choosing the design).
- First-pass gate FAIL → fixes: tenant-isolation killer test for the stats
  SQL (`test_stats_never_count_another_users_findings`), latest-application
  killer test (`test_stats_use_the_latest_application_per_finding`), and `""`
  added to the parity-matrix outcomes. Reviewer's mutant probes (isolated
  copy): all three mutants dead.
- Bug caught by the live-PG arm during development: an early `_iso_ms_z`
  draft used `%f` (microseconds) where seconds belonged — SQLite accepted the
  malformed text silently, PG's timestamp cast rejected it. Fixed before the
  gate; recorded here as evidence the dual-dialect parity tests earn their
  keep.
