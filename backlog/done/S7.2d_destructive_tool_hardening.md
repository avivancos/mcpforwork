# S7.2d — Destructive-tool hardening: delete_my_data two-step

**Epic:** MCP / safety
**Estimated effort:** ~2 h

## Goal

Autopilot promotes the ADR 0001 ledger item to P0: `delete_my_data` is
agent-reachable with a bare boolean. Mirror the consent pattern: the
destructive call becomes two-step — a summary + short-lived confirm token,
then execution with that token.

## Spec

- ALSO IN SCOPE (from the S7.2b review): the L2 cap count+flip TOCTOU —
  `_l2_authorized_today` and the consent_level flip are not atomic between
  themselves, so N parallel `request_submit` calls on distinct pre-staged
  applications could each pass the cap check. Serialize count+flip (single
  conditional statement or per-user serialization) with a two-connection
  concurrency test; the same test should pin the exactly-once property of
  the atomic `consent_level` guard (the mutant the sequential suite cannot
  kill).
- `delete_my_data()` (no token) → returns a summary of what would be
  deleted (row counts per table) + a short-lived `confirm_token`
  (single-use, expires in 5 min, stored server-side hashed — same pattern
  as magic-link tokens).
- `delete_my_data(confirm_token=...)` → executes the deletion; invalid /
  expired / reused token → structured error, nothing deleted.
- The bare `confirm=True` boolean path is REMOVED (breaking change on an
  MCP tool — acceptable pre-1.0; guidance updated in the same card).
- Token store: reuse the existing token-table pattern (magic_link_tokens)
  or a small dedicated table if shapes diverge — justify on the card.
- Audit: both the request and the execution write audit rows; the execution
  row is written BEFORE the delete (the delete wipes the user's rows).
- Guidance + `/apply` prompt: never call with a token the user didn't just
  read aloud / paste; the two-step is the consent gate for destruction.

### Gate finding dispositions

- **P2-1 (surviving mutant b) — written rejection.** The `used_at IS NULL`
  guard is behaviorally unreachable today: every successful mark is followed
  by the erase of the token row in the SAME transaction, so a concurrent
  loser's UPDATE matches 0 rows on both dialects (PG: tuple dead after
  unblock; SQLite: row gone after busy-wait) and is refused via
  `rowcount != 1` regardless; a post-commit retry hits the `used_at IS NOT
  NULL` pre-check. The guard stays as defense in depth for any future
  mark-without-erase path; no test can kill the mutant without such a path.
- **P2-2 (token provenance) — acknowledged limitation, recorded.** The
  confirm_token is returned in the MCP tool response, i.e. into the agent's
  context: a prompt-injected agent could chain step 1 → step 2 without a
  human act. The two-step is a strong friction/auditability gate (it kills
  the bare-boolean P0: destruction now requires threading a server-minted,
  single-use, 5-min value across two deliberate calls, both audited) but it
  is NOT an ADR-0005-provenance-bound consent artifact. The dashboard delete
  path (human session + typed confirmation) remains the human-bound
  equivalent. Follow-up candidate on the hosted track: dashboard-minted
  delete confirmations.
- **P3s — all fixed in this card:** boundary test at exactly `expires_at`
  added (the `>=` makes the 300th second expired; one second before still
  redeems); misnamed test renamed to
  `test_execute_deletion_erases_its_own_token_rows`; `audited_as` now
  asserted in the boundary test.

## Design decisions (recorded at implementation)

- **Token store: dedicated `delete_confirm_tokens` table** (migration 12 +
  PG twin, FORCE RLS), NOT `magic_link_tokens` — mixing token kinds would
  let a login token replay as a delete confirmation (and vice versa). Same
  shape/pattern otherwise (sha256 hash only, epoch expiry, atomic
  single-use mark). On Postgres the table IS RLS-forced (unlike
  magic_link_tokens): tokens are only minted/redeemed inside an
  authenticated tenant context, so RLS makes a cross-tenant token
  invisible and the service's user_id check is defense in depth.
- **API `/v1/account/delete` keeps calling `delete_user_data` directly**:
  the dashboard path is the human's own session behind a typed-DELETE
  confirmation UX — that IS the two-step equivalent for a human. The token
  flow guards the agent-reachable path (the MCP tool), which is where a
  bare boolean was the P0.
- **TOCTOU fix: per-user serialization via `UPDATE users SET id = id`**
  at the top of the L2 policy branch in `request_submit`. Portable across
  dialects (SQLite: database-wide writer lock; Postgres: row lock + READ
  COMMITTED re-snapshot of the count after unblocking). Chosen over a
  conditional UPDATE with a COUNT subquery because that subquery would
  still read a pre-lock snapshot under Postgres READ COMMITTED.
- **Test determinism lesson (recorded for future concurrency tests)**:
  `connect()` runs migrations whose trailer `PRAGMA user_version = N` is a
  database-header WRITE — connections opened mid-race serialize on the
  handshake, hiding the race. Racer connections must use
  `run_migrations=False` and be created in their own thread
  (`check_same_thread`). The deterministic killer holds T1's transaction
  open across T2's whole call (two Events, 5s hold).
- **Mutant probe (recorded per AGENTS.md §4)**: users-lock line removed →
  `test_a_second_submit_counting_mid_first_transaction_is_refused_by_the_cap`
  FAILED (2 authorized over cap 1); restored → 3/3 green.

## Improvements noted
- The barrier-synchronized parallel test is an end-state pin, not the
  mutant killer (thread startup dominates microsecond critical sections);
  the interleaved two-transaction test is the deterministic one.
