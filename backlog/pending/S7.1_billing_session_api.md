# S7.1 — Billing: Stripe session + portal + webhook (server)

**Epic:** Hosted — Monetization (Sprint 7)
**Owner:** SERVER track (Python). The web funnel (W5.1) is already built against
this contract on the fixtures seam; delivering this endpoint flips it live with
no web change.

## Goal

Implement the Stripe billing backend behind the parity endpoint the web
dashboard already calls: create Checkout + Portal sessions, and handle the
webhook that flips subscription state. Single flat $5/mo plan, 7-day trial.

## Contract (what the web already expects)

- **`POST /v1/billing/session`** — body `{ "kind": "checkout" | "portal" }`,
  authenticated (session cookie). Returns `{ "url": string }`.
  - `checkout`: a Stripe Checkout Session for the $5/mo price with a 7-day trial
    (`subscription_data.trial_period_days = 7`), `success_url =
    <SITE>/account/billing?checkout=success`, `cancel_url =
    <SITE>/account/billing?checkout=canceled`. URL host is `checkout.stripe.com`.
  - `portal`: a Billing Portal Session, `return_url = <SITE>/account/billing`.
    URL host is `billing.stripe.com`.
  - The web guards the returned URL to https + `{checkout,billing}.stripe.com`
    (`web/src/lib/safeRedirect.ts`) — keep the real URLs on those hosts.
- **`GET /v1/subscription`** — returns `{ status: "trial"|"active",
  trialDaysLeft: number, price: "$5/mo" }` (already consumed by the dashboard).
- **`POST /v1/billing/webhook`** — Stripe webhook (signature-verified) that
  advances subscription state on `checkout.session.completed`,
  `customer.subscription.updated/deleted`, `invoice.payment_failed`.

## Notes / invariants

- Never store card data (Stripe Checkout/Portal hold it) — the Security page
  and Privacy policy already commit to this.
- Fair-use infra limits only (storage/findings counts), never LLM limits
  (PRODUCT_PLAN §Hosted architecture).
- Ports the donor card-9 Stripe patterns (checkout/portal/webhook) per the plan.

## Carried from the W5.1 gate (reviewers, must honor here)

- **Entitlement is webhook-driven, never param-driven (security-reviewer P3).**
  The `?checkout=success` return param only shows a UI acknowledgment banner — it
  MUST NOT grant, flip, or infer subscription state. Plan/entitlement is written
  only by the verified webhook (`checkout.session.completed` etc.). Keep
  `success_url`/`cancel_url` pointing solely at `/account/billing?checkout=…` (no
  session tokens or entitlement data in the query string).
- **Avoid the contradictory "subscribed" + "trial ends in N days" render
  (code-reviewer P2).** Stripe redirects the browser to `success_url`
  synchronously, but the webhook that flips `GET /v1/subscription` to `active`
  lags by seconds. In that window the billing page (`billing/page.tsx`) would show
  the green "You're subscribed" banner directly above the trial nudge. When the
  server lands, reconcile: either the billing page suppresses the trial nudge when
  `checkout==="success"`, or the success copy reads "Payment received —
  activating…" until `subscription.status==="active"`. (Web-side one-liner; noted
  here so it's not lost — the two surfaces ship together.)
