# S1.3 — Profiles schema (intake model) + profile services

**Epic:** Sprint 1 — Data core (organ transplants)
**Estimated effort:** ~4 h

## Goal

The `profiles` data model implementing §Onboarding intake model — Tier 1
(required, <3 min) and Tier 2 (progressive), the achievements bank, and the
style profile — plus the profile services the MCP tools will wrap in S2.2.

## Spec

- Migration adding: `profiles` (Tier 1 fields: name, email, country, city,
  work authorization + visa flag, target titles 1–5, sectors, seniority,
  employment type, work mode + relocation, minimum salary
  {amount,currency,period} PRIVATE, languages+proficiency, cv_text; Tier 2
  fields nullable: urls, availability/notice, deal-breakers, career
  narrative, salary public/floor), `achievements` (metric, context, role),
  `style_profile` (writing sample + derived directives), `star_stories`.
  All per-user tables carry `user_id` (RLS-ready per S1.2 policy pattern).
- Services (signature style `(uow, user_id, ...)`, caller commits):
  `get_profile`, `update_profile` (partial, validates enums), `list_profiles`,
  `set_active_profile`, `add_achievements`, `set_style_profile`.
- Multi-profile support: one active profile per user
  (donor pattern: `src/radar/services/profiles.py` — reference only, that
  module is tech-persona-hardcoded; the new schema is sector-agnostic BY
  DATA: titles/sectors are user data, not code).
- Privacy rule encoded now: minimum salary and EEO-class fields are never
  included in any export destined for generation briefs without an explicit
  consent flag (test asserts the service-level redaction).
