# S4.1 — Application state machine + start_application preflight

**Epic:** Sprint 4 — Browser-apply orchestration
**Estimated effort:** ~4 h
**State:** pending

## Goal

The server choreographs, the client's browser acts. `start_application` runs
the deterministic preflight (dedup gate, daily cap, playbook, candidate data)
and returns an application session with an ordered step plan. THE consent
invariant is structural: **no submit-class step is ever emitted here** — only
`request_submit` (S4.3) can authorize/route submission.

## Spec

- Migration v6: `applications` (id, user_id, finding_id→explore_findings,
  state, apply_method, consent_level INT DEFAULT 0, steps TEXT/JSON,
  current_step INT, outcome, evidence, created_at, updated_at) + FORCE RLS;
  `ALTER TABLE profiles ADD COLUMN form_answers TEXT` (JSON; progressive
  Q&A store for resolve_field). PG twin.
- `domain/apply_flow.py` (PURE): states `draft→filling→awaiting_human→
  submitted→verified` (+`abandoned`); `ALLOWED_TRANSITIONS`;
  `build_steps(finding, profile, assets, playbook)` → ordered
  `[{step_id, kind: navigate|fill|answer|review|verify, instruction,
  value_ref?, evidence}]` — kinds exclude `submit` BY CONSTRUCTION (module
  test greps the builder output space).
- `services/apply.py`: `start_application(uow, user_id, finding_id)` —
  gates: finding exists+approved, check_seen not applied, daily cap
  (MAX_APPLICATIONS_PER_DAY=10 module const), assets exist warning; loads pack
  apply_playbook by source_slug; persists the application (state `filling`);
  returns `{application_id, state, consent_level: 0, steps, next_action}`.
- MCP tool `start_application`.

## Definition of Done

- [ ] No step from build_steps ever has kind 'submit' (property test over
      representative inputs)
- [ ] Preflight blocks: unapproved finding, already-applied URL (dedup gate),
      daily cap reached (11th today → error)
- [ ] State transitions validated; invalid transition rejected
- [ ] RLS live on applications; parity both backends; gate 4/4
